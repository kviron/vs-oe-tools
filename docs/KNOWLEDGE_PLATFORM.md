# Платформа знаний для ИИ-агентов

> Статус: черновик архитектурного контракта.
>
> Этот документ описывает целевую модель. Он не означает, что хранилище,
> индексирование или MCP-инструменты уже реализованы.

## 1. Цель

Платформа должна помогать агентам находить и проверять технические и
бизнес-знания Восточного Экспресса при росте числа проектов, версий баз,
метаданных, исходников и производственных задач.

Расширение `vc-ve-tools` остается клиентом платформы и точкой интеграции с
агентами. Основное хранилище знаний не встраивается в VSIX и не привязывается к
жизненному циклу конкретной версии расширения.

## 2. Базовые решения

1. **Живые факты читаются из первичного источника.** Активная база, текущий код,
   метаданные, состояние клиента и задач проверяются существующими MCP-
   инструментами во время работы агента.
2. **Долгоживущие знания версионируются отдельно.** Бизнес-правила, причины
   решений, эксплуатационные инструкции и проверенные расследования хранятся с
   историей изменений и доказательствами.
3. **Поисковые индексы не являются источником истины.** Полнотекстовый и
   векторный индексы должны полностью перестраиваться из исходных записей.
4. **Основой служат сущности и связи.** Документы связываются со стабильными ID
   классов, методов, атрибутов, пакетов, задач, релизов и профилей баз.
5. **Знание имеет область применимости.** Нельзя выдавать правило без учета
   версии продукта, профиля базы, периода действия и статуса проверки.
6. **Агент предлагает, человек подтверждает.** Автоматически найденный факт не
   становится проверенным знанием без контролируемого review.

## 3. Источники и уровень доверия

| Источник | Что из него берется | Как используется |
| --- | --- | --- |
| PostgreSQL проекта | актуальные метаданные и данные | читается на момент запроса |
| PKF, Pascal, DFM и SVN | код, структура пакетов и история | индексируется по ревизиям и при необходимости перечитывается |
| Производственные задачи | требования, обсуждения и результат работ | связывается с сущностями, но не считается доказательством текущего состояния |
| Проверенная документация | бизнес-правила и объяснения | долговременное знание с владельцем и датой проверки |
| Вывод агента | кандидат в новое знание | сохраняется только как предложение |

При конфликте сохраненной статьи с текущим состоянием первичного источника агент
должен показать конфликт, а не незаметно выбрать одну из версий.

## 4. Идентичность сущностей

У каждой сущности есть тип и стабильный внешний идентификатор:

```text
class:8921658
method:3200110
attribute:12992431
task:88212
package:SysPackage
database-profile:oetrunk3_6
release:3.6
business-rule:document-calculation.duplicates
```

Человекочитаемые имена и псевдонимы не используются как идентичность: они могут
изменяться и совпадать. Для сущностей без штатного числового ID применяется
стабильный строковый ключ, не зависящий от заголовка документа.

Канонический ID вычисляется как `<type>:<externalId>` и не дублируется в самой
ссылке на сущность. Это исключает расхождение типа, внешнего и канонического ID.

Связь между сущностями содержит собственный тип, источник и период действия.
Минимальный набор отношений:

- `belongs_to` — член принадлежит классу или пакету;
- `implements` — техническая сущность реализует бизнес-правило;
- `references` — сущность ссылается на другую сущность;
- `changed_by` — сущность изменена в рамках задачи или ревизии;
- `applies_to` — знание относится к релизу или профилю базы;
- `supersedes` — новая запись заменяет прежнюю.

## 5. Минимальная запись знания

Независимо от физического формата запись обязана содержать:

Машинно-читаемый контракт первого среза находится в
[`knowledge/schema/knowledge-record.schema.json`](knowledge/schema/knowledge-record.schema.json),
а проверяемые примеры — в [`knowledge/examples`](knowledge/examples).

```yaml
id: business.document-calculation.duplicates
type: business-rule
title: Запрет дублирования расчетов предложения
status: proposed
summary: Краткое утверждение, которое сможет найти агент.
content: Полное описание правила и его ограничений.

applicability:
  releases: []
  database_profiles: []
  valid_from: null
  valid_to: null

entities: []
relations: []
sources: []

verification:
  method: null
  verified_at: null
  verified_by: null

owner: null
created_at: 2026-09-16T00:00:00Z
updated_at: 2026-09-16T00:00:00Z
```

Пустая область применимости означает «не установлена», а не «подходит ко всем
версиям». Такая запись не может получить статус `verified`.

## 6. Жизненный цикл доверия

Допустимые статусы:

- `draft` — незавершенная ручная запись;
- `proposed` — оформленное предложение агента или человека;
- `verified` — проверено ответственным владельцем;
- `disputed` — обнаружено содержательное противоречие;
- `deprecated` — правило заменено или больше не рекомендуется;
- `expired` — закончился установленный период применимости.

Переход в `verified` требует источника, области применимости, способа проверки,
владельца и даты проверки. Изменение содержательного утверждения создает новую
версию и требует повторной проверки.

## 7. Поиск и сбор контекста

Целевой поиск является гибридным и выполняется в следующем порядке:

1. точный поиск ID и именованных сущностей;
2. фильтрация по правам, релизу, профилю базы, периоду действия и статусу;
3. переход по явно сохраненным связям;
4. полнотекстовый поиск;
5. семантический поиск;
6. объединение, устранение дублей и переранжирование;
7. проверка изменчивых фактов через живой MCP.

Результат поиска должен включать не только текст, но также ID записи, статус,
область применимости, источники, дату проверки и использованные связи.

## 8. Граница хранения

Целевая серверная реализация может использовать PostgreSQL для записей,
версий, связей и аудита, полнотекстовый индекс для лексического поиска и
`pgvector` для семантического поиска. Конкретный поисковый движок скрывается за
внутренним интерфейсом и может быть заменен без изменения MCP-контракта.

Локальное хранилище расширения является только ограниченным кешем. Оно не должно
быть единственным экземпляром базы знаний и не должно содержать секреты доступа
к центральному сервису внутри VSIX.

## 9. Граница MCP

Публичный контракт планируется небольшим и предметным:

- поиск записей с обязательными фильтрами применимости;
- чтение полной записи по ID и версии;
- получение контекста для сущности;
- объяснение связи между сущностями;
- проверка свежести источников;
- создание предложения;
- регистрация обнаруженного противоречия.

Названия и схемы MCP-инструментов будут зафиксированы отдельным решением перед
первой реализацией. До этого момента они не считаются публичным API.

## 10. Первый вертикальный срез

Первая реализация должна быть только читающей и доказать один сценарий:

> По ID класса, метода или задачи агент находит связанные проверенные знания и
> получает их вместе с источниками и областью применимости.

В этот срез не входят embeddings, автоматическое извлечение знаний, запись через
MCP, UI управления, фоновая синхронизация и отдельная графовая СУБД. Их добавляют
только после проверки базовой модели идентичности и применимости на реальных
данных.

## 11. Критерии готовности следующего шага

Перед реализацией хранилища необходимо согласовать:

- типы сущностей первого среза;
- формат ссылок на источники;
- обязательные поля области применимости;
- правила выдачи `proposed`, `deprecated` и конфликтующих записей;
- место размещения канонических записей знаний.
