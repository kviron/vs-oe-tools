# Контракт локальной истории задач, версия 1

Локальная история в `work-history.sqlite` помогает человеку быстро восстановить ход работы,
а агенту — найти точные изменения и проверки без чтения старого контекста чата.
Она не заменяет production-карточку задачи, исходный код, активную базу или статью базы знаний.

## Идентификатор и источники истины

- Ключ записи: `(workspace, task_number)`. Для ссылки `https://r.oe-it.ru/88405` номер — `88405`.
  Если номера production-задачи нет, нужен устойчивый идентификатор проекта, например `vc-ve-tools-2026-09-28-history-ui`.
- `workspace` — абсолютный путь рабочей копии, переданный MCP. Номер может повторяться в разных рабочих пространствах;
  при неоднозначном поиске агент указывает workspace явно.
- Строка `tasks` — **локальная история работы агента**. Поле `status=completed` означает завершение локальной работы,
  а не изменение статуса production-карточки, публикацию или синхронизацию пакетов.
- Production-карточка через `get_production_task` задаёт текущие требования и её актуальный статус.
  Текущий код, профиль, база и состояние среды проверяются отдельно. При расхождении источников агент показывает расхождение.
- Статья Git или иная подтверждённая запись базы знаний хранит обобщённое правило. Кандидат и флаг переноса — разные состояния.

## Структура записи `tasks`

| Поле MCP | Поле SQLite | Правило заполнения |
| --- | --- | --- |
| `taskNumber` | `task_number` | Точный номер или устойчивый идентификатор; без описательного текста. |
| `title` | `title` | Короткое название предмета работы, без слова «готово», если работа продолжается. |
| `status` | `status` | `in_progress`, `blocked` или `completed`; статус production отдельно. |
| `agentWorking` | `agent_working` | `true` только пока агент активно работает; при паузе и блокировке `false`, при завершении сбрасывается автоматически. Индикатор виден 15 минут после последнего обновления записи. |
| `summary` | `summary` | 1–3 предложения: задача, фактический итог, важная граница. Не переписывать исходную карточку целиком. |
| `progress` | `progress` | Текущее положение и следующий конкретный шаг; обновляется при продолжении работы. |
| `changes` | `changes` | Краткий Markdown-обзор реализованного: объект/файл, ID, действие, результат. Подробности — в `task_changes`. |
| `verification` | `verification` | Краткий Markdown-обзор фактических проверок и их границ. Подробности — в `task_verifications`. |
| `limitations` | `limitations` | Что не проверено, не синхронизировано или осталось выполнить; пустая строка только если таких пунктов нет. |
| `databaseProfile` | `database_profile` | Точно установленный профиль, если он относится к работе; не выводить из пути или предположения. |
| `sources` | `sources_json` | Массив точных URL, путей, объектных ID/локаторов и ревизий; не добавлять недоступный источник как проверенный. |

Все содержательные текстовые поля могут содержать **Markdown**. Для удобства человека использовать короткие абзацы,
маркированные списки, обратные кавычки для ID/путей/команд и кодовые блоки с языком (`pascal`, `pkf`, `sql`, `typescript`, `text`).
Ссылки оформлять Markdown-ссылками. Не вставлять HTML, большие логи, секреты или полный исходный код.
Перед каждым блоком исходника метода указывать проверенный числовой ID метода. В строке открытия блока
дублировать его как `method=123456`: интерфейс покажет ID над кодом и позволит открыть метод по нажатию.
Если ID неизвестен, сначала разрешить его через MCP; не подставлять номер задачи или ID класса вместо ID метода.

````markdown
Метод ID: 123456

```pascal method=123456
procedure TExample.Run;
begin
  // Фрагмент, относящийся к задаче.
end;
```
````

Каждое поле отвечает только за свой смысл: не копировать один и тот же текст в `summary`, `changes` и `verification`.

## Связанные записи и доказательства

| Таблица | Когда добавлять | Минимальное содержание |
| --- | --- | --- |
| `task_entities` | Найден стабильный объект, класс, метод, пакет или релиз | Тип, точный ID, роль в задаче и понятная подпись. |
| `task_changes` | Выполнено конкретное изменение | Что изменено, точный `source_locator`, ревизия при наличии. Не считать намерение изменением. |
| `task_verifications` | Выполнена проверка | Метод, наблюдаемый результат, `passed`/`failed`/`partial`, профиль/релиз/источник при применимости. Сборка и runtime — разные проверки. |
| `task_decisions` | Выбор пригодится при следующей работе | Решение, причина, рассмотренные альтернативы; неизвестные альтернативы — пустая строка. |
| `work_events` | Значимый промежуточный результат или блокировка | Тип события и короткий факт; не дублировать каждое сообщение чата. |
| `knowledge_candidates` | Найдено повторно применимое правило | Название, краткое правило, зачем сохранить и откуда оно взято. Кандидат не является опубликованным знанием. |
| `tool_calls` | Автоматический аудит MCP | Только имя, успех и длительность; без аргументов, тел ответов и секретов. |

Нельзя помечать проверку `passed`, если она не запускалась или её результат неизвестен.
`partial` означает, что перечислены как подтверждённые факты, так и непроверенная часть.
Проверка привязывается к тому окружению, где она действительно выполнялась.

## Жизненный цикл

1. В начале работы вызвать `save_task_progress` со статусом `in_progress`, `agentWorking: true`, названием и текущим шагом.
   Добавить ссылку на карточку, если она доступна.
2. После значимого действия обновить `progress`; отдельно записать изменение, проверку или решение соответствующим MCP-инструментом.
   При паузе поставить `agentWorking: false`; при возобновлении снова `true`. При реальной блокировке поставить `blocked` и записать препятствие и условие продолжения.
3. После выполнения локальной работы вызвать `save_completed_task`. Заполнить итог, изменения,
   проверки и ограничения. `completed` не утверждает, что production-задача закрыта или опубликована.
4. Если работу возобновили, снова поставить `in_progress` и явно указать, что изменилось после прежнего завершения.
5. Кандидат в знания сначала проходит проверку. Только после подтверждённой записи статьи обновить его статус
   и вызвать `mark_task_knowledge_transferred` с устойчивой ссылкой. Задача остаётся доступной для поиска.

После успешного сохранения агент сообщает номер и **локальный** статус записи. При ошибке сохранения этого не утверждает.

## Порядок чтения для агента

1. Из номера или ссылки взять точный `task_number`. Искать его в локальной истории через `search_completed_tasks`,
   затем читать запись через `get_completed_task` и подробности через `get_task_context`.
2. Запросить актуальную production-карточку через `get_production_task` даже при найденной локальной истории.
3. Для планируемого изменения объекта проверить `find_tasks_for_entity`, затем текущий код и нужное окружение.
4. В ответе различать «из локальной истории», «из production-карточки» и «проверено сейчас».

## Пример короткой карточки

```text
taskNumber: 88405
title: Проведение выбранных счетов
status: completed
summary: Два выбранных счёта переведены в состояние «Проведен». Локальная работа завершена.
changes: - Проведены два выбранных счёта; точные ID указать только после проверки источника.
verification: - В целевой среде подтверждено состояние «Проведен» для обоих счетов.
limitations: Production-карточка остаётся «В работе»; пакетные файлы ещё не синхронизированы.
sources: ["https://r.oe-it.ru/88405"]
```

Пример показывает форму записи, а не повторную проверку фактов по задаче 88405.

## Совместимость и развитие

Версия 1 описывает существующие поля SQLite и MCP. Новые обязательные поля, перечисления или правила миграции
требуют новой версии контракта и совместимого чтения старых записей. Рендерер Markdown отвечает только за отображение:
структурные поля и связанные таблицы остаются основой поиска и автоматического анализа.
# SVN commits

`svn_task_commits` stores one row per task number, repository root, and revision, independently of a local work-history task. `svn_task_scans` records successful scans by task number and workspace, including scans with no matches. Existing `task_svn_commits` and `task_svn_scans` rows migrate into these shared tables once. The task number must lead the first nonempty line of the SVN log message (for example, `88405 - ...`); a merge summary that mentions the number later does not belong to the task. Cached rows from older scans are filtered on read and pruned on refresh. Both task cards use this cache and allow manual refresh. Agents can read cached rows and scan history from any workspace with `get_task_svn_commits` or update them with `refresh_task_svn_commits`; refresh may need an explicit SVN workspace path. A commit proves only that the SVN repository recorded that revision; it does not prove deployment or runtime behavior.
