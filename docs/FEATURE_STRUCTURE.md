# Структура функций расширения

`src/extension.ts` реализует контракт VS Code `activate(context): Promise<void>`.
`src/application/activate.ts` — дирижёр запуска: он вызывает именованные этапы
в порядке зависимостей, передаёт их результаты следующему этапу и ждёт
обязательной готовности. В нём нет создания сервисов, регистрации команд,
панелей и событий, владения `Disposable` или предметных callback.

Этапы `bootstrap.ts`, `editors.ts`, `features.ts`, `navigation.ts`, `mcp.ts`,
`workbench.ts` и `workspace.ts` выполняют сборку и связи между фичами. Их порядок виден в
`activate.ts`. Логика отдельной фичи и её регистрации живёт в `src/features`.
Новая строка в `activate.ts` допустима, только если она запускает этап,
передаёт его результат или ожидает его готовности.

## Алиасы и общий код

- В коде Extension Host (`src`) используем `#app/*` для импортов от корня `src`.
  Алиас настроен в TypeScript, esbuild и `package.json#imports`, чтобы работать
  также в JavaScript, который `tsc` создаёт для тестов в `out`.
- В webview сохраняем существующий `@/*` от `webview-ui/src`; его используют
  Vite и shadcn-vue. Алиасы двух сред не смешиваем.
- Общие Vue-компоненты находятся в `webview-ui/src/components`, примитивы
  shadcn-vue — в `components/ui`, общие функции интерфейса — в `lib`.
- Для кода Extension Host `shared` выделяем только под чистые утилиты и типы,
  которые не принадлежат конкретной фиче и не зависят от VS Code или базы.
  Предметные модели и сценарии остаются в фичах; доступ к БД остаётся в
  `infrastructure`. Пустой слой заранее не создаём.

## Единый шаблон

```text
src/features/<feature>/
  index.ts      публичный API для других функций и application
  register.ts   вход функции: команды, представления, подписки, dispose
  models.ts     типы предметной области
  session.ts    доступ и состояние сеанса, если они нужны
  capture.ts    отдельный сценарий, если он достаточно велик
```

Создавать каждый файл из шаблона не требуется. Один сценарий может помещаться
в `register.ts`; отдельный файл нужен, когда у кода появляется своя обязанность.
Имена короткие, потому что область уже задана именем папки. Существующие файлы
с более длинными именами можно переименовывать постепенно, при работе с ними.

`register.ts` получает явные зависимости, регистрирует точки входа VS Code и
помещает созданные `Disposable` в `context.subscriptions`. Наружу он возвращает
только действия, нужные другим функциям. Репозитории и интеграции не должны
зависеть от `src/application` или конкретных представлений.

В `index.ts` перечисляем только используемые снаружи значения и типы. Импорты
между разными функциями и из `application` идут через этот файл. Внутри самой
функции используются прямые относительные импорты, чтобы не создавать цикл
через собственный `index.ts`. Тесты могут обращаться к внутренним модулям.
Публичный API добавляется по мере переноса внешних импортов, без экспорта всей
папки через `export *`.

Перед новым выделением модуля формулируем его одну ответственность и минимальный
контракт для потребителей. Модуль отвечает за одну функциональную область;
несвязанные сценарии разделяем. Из `index.ts` экспортируем только то, что
действительно используют соседи. Дополнительный слой нужен лишь тогда, когда у
него есть собственная ответственность, а не ради перенаправления вызова.

## Пример: production-задачи

- `register.ts` создаёт панель, команду, кнопку Activity Bar, реакцию на настройки
  и действия для истории кода, навигации и MCP.
- `session.ts` получает настройки подключения, работает с `SecretStorage` и
  выполняет интерактивный импорт захвата.
- `capture.ts` читает метаданные захвата и проверяет сохранённую авторизацию.
- `agent.ts` формирует ответы о задачах для инструментов агента; доступ к
  соединению и логгеру остаётся внутри фичи. Через `register.ts` наружу выходят
  только три действия `agentActions`.
- `queries.ts` строит запросы в диалекте Восточного Экспресса, `auth.ts`
  формирует параметры OENP-авторизации, `connection.ts` отвечает за TCP-обмен,
  `oenpSession.ts` открывает авторизованную сессию и закрывает её после запроса,
  `mapping.ts` преобразует строки ответа, а `productionTasksRepository.ts`
  собирает операции загрузки. Файлы панелей отвечают только за отображение.

## Пример: действия агента

`src/features/ai/actions.ts` только собирает единый контракт действий для
встроенных инструментов VS Code и локального navigation bridge. Предметные
сценарии находятся в `agent.ts` соответствующих фич: классов, методов, модулей,
синхронизации пакетов, production-задач, истории кода, жизненного цикла,
проекта и настроек HTTP-теста. Зависимости передаются явно из
`src/application/navigation.ts`; проверки ожидаемой базы и прочие ограничения
остаются у владельцев действий. Регистрация инструментов и запуск моста
выполняются после создания этого контракта.

Локальный мост разделён по одной ответственности на модуль: `navigationBridge.ts`
владеет сервером и файлом адреса, `navigationHttp.ts` проверяет HTTP-маршрут,
токен и размер тела, `navigationRequest.ts` проверяет входные поля,
`navigationRoute.ts` вызывает действие и формирует ответ. Внешний контракт
`startNavigationBridge()` не меняется; файл адреса удаляется только если его
токен всё ещё принадлежит этому экземпляру моста.

## Структура MCP

MCP-код сгруппирован в `src/mcp/database`, `src/mcp/client`,
`src/mcp/queries` и `src/mcp/tools`. В `database/profile.ts` синхронизируются
рабочая папка и профиль, `pool.ts` управляет подключениями, `context.ts`
связывает выбранную базу с клиентом, `queries.ts` выполняет запросы в
транзакции `READ ONLY`. `database/index.ts` — публичный вход для MCP-инструментов.
`database/sql.ts` помечает статические шаблоны SQL для подсветки; значения
передаются отдельно через `$1`, `$2` и массив параметров.
Подсветка `sql`-шаблонов в JS/TS включена через injection grammar в
`syntaxes/sql-tagged-template.tmLanguage.json`. Грамматика взята из
`frigus02/vscode-sql-tagged-template-literals` (коммит
`b7729d96b5e180fc8a2610e78113422f51b183e8`, MIT); текст лицензии находится
в `syntaxes/sql-tagged-template.LICENSE`. Для нашего расширения изменено только
имя scope грамматики.
В `client` находятся HTTP-транспорт и жизненный цикл нативного MCP, в `queries`
— запросы и преобразование метаданных.
Инструменты в `tools` сгруппированы по области работы: `database`, `classes`,
`methods`, `sources`, `packages`, `lifecycle`, `project`, `client`, `http`,
`navigation` и `diagnostics`. Каждый файл регистрирует один инструмент.
`tools/registration.ts` сохраняет единый порядок регистрации, а `catalog.ts`
строит каталог для настроек из тех же регистраций. `tools/index.ts` экспортирует
только эти два публичных действия и тип элемента каталога.

## Жизненный цикл проекта

- `src/features/project/credentials.ts` хранит способ чтения и обновления
  учётных данных клиента через настройки и `SecretStorage`.
- `src/features/project/register.ts` создаёт панель настроек, команды проекта и
  строку состояния; наружу отдаёт панель и управление кодировкой.
- `src/features/project/selection.ts` публикует выбранный профиль для текущего
  рабочего пространства и активного окна.
- `src/features/ai/runtime.ts` публикует runtime-состояние MCP после запуска
  navigation bridge.
- `src/application/navigation.ts` создаёт действия агента, регистрирует
  инструменты и запускает локальный мост. `src/application/mcp.ts` после этого
  публикует состояние MCP и регистрирует сервер; наружу отдаёт только действие
  повторной публикации для событий жизненного цикла.
- `src/application/lifecycle.ts` слушает события VS Code и вызывает
  обработчики в порядке: смена базы, обновление MCP, кодировка проекта.
  `src/application/databaseChange.ts` публикует выбранную базу, закрывает
  зависящие от неё панели и обновляет представления. MCP и кодировка обрабатываются
  в своих модулях. При смене активного окна и набора папок сначала публикуется
  активная база, затем состояние MCP.

## Проводник объектов

`src/features/explorer/register.ts` создаёт представление проводника и
подключает действия редакторов, классов и пакетов. Там же регистрируется
переход к объектам из буфера обмена после создания production-задач, от которых
зависит поиск ссылок на задачи.
Проводник получает от production-задач только `searchTasks` и `showTask`; он не
читает настройки OENP, не владеет логгером задачи и не вызывает её репозиторий.

## Остальные точки входа

`package-sync`, `sql-executor` и `native-logs` регистрируют свои панели в
собственных `register.ts`. Этапы `application` вызывают эти функции и
хранят связи между фичами. Для `classes`, `methods`, `modules`, `dfm`,
`code-history`, `sql-monitor`, `packages` и `spu` добавлены узкие `index.ts` с
действиями, которые сейчас нужны `application`.

`classes/register.ts` владеет настройкой взаимодействия классов с редакторами
и учётными данными; наружу для запуска отдаётся только `registerClasses`.
Поиск production-задачи по ссылке и сообщение об отсутствии задачи остаются
в `production-tasks`, а история кода получает готовое действие `openReference`.

Команды выбора и проверки базы и установки ID пользователя принадлежат `project`,
команда открытия SQL Monitor — `sql-monitor`, копирование ID из проводника —
`explorer`. `application/workspace.ts` только регистрирует их в нужном порядке.

`application/workbench.ts` подключает представления, редакторскую навигацию и
восстановление карточек классов; наружу отдаёт только панель синхронизации,
нужную обработчику смены базы. `application/workspace.ts` запускает реакции на
изменение рабочего пространства, применяет начальную кодировку и регистрирует
команды их владельцев.

При следующем переносе сохраняем порядок регистрации, идентификаторы команд,
момент чтения настроек и освобождение ресурсов. Проверяем TypeScript, ESLint и
поведение в Extension Development Host для затронутых сценариев.
