# Аудит registerSettings и SettingsViewProvider

Дата: 2026-10-01. Проверена текущая рабочая копия, включая незакоммиченные изменения. Исполняемый код не изменён. Приоритеты: P1 — исправить в первую очередь; P2 — исправить после этого; P3 — улучшение архитектуры.

## Вывод

`registerSettings` — нормальная точка сборки области: создаёт два сервиса и UI, регистрирует две команды и передаёт освобождение провайдера в `context.subscriptions`. Разносить эту небольшую функцию по дополнительным фабрикам оснований нет. Основная сложность находится в `SettingsViewProvider` (451 строка) и в координации клиентского MCP. Выделение `SettingsProjectActions` и `SettingsServices` уже сократило зависимости UI от проекта, но само по себе не устранило гонки и побочные эффекты обновления состояния.

Цепочка: `registerFeatures → registerSettings → SettingsViewProvider`; сервисы `ClientMcpService` и `HttpApiService` создаются в `registerSettings`. UI обращается к операциям проекта через `SettingsProjectActions`. Действия HTTP для агента идут через `createHttpTestAgentActions → SettingsViewProvider → HttpApiService`, поэтому операция сервиса может ожидать обновления UI.

## 1. P1: обновление состояния может повторять SQL после ошибки

Источники: `settingsViewProvider.ts:37,333,359`; `httpApiService.ts:31`; `httpMethodRepository.ts:24`; `databaseQueryExecutor.ts:64`; `extensionLogService.ts:103,125`.

Провайдер слушает **каждое** изменение журнала и вызывает `postState`. `getState` безусловно загружает HTTP-каталог через SQL, даже когда открыта только панель настроек. Если запрос дошёл до PostgreSQL и завершился ошибкой, монитор передаёт ошибку в журнал, журнал вызывает подписчика и начинается следующий `getState`. Обработка ошибки в `loadMethodsForState` не разрывает эту цепочку: событие уже отправлено. При устойчивой SQL-ошибке возможен поток запросов и записей журнала без ожидания десятисекундного таймера.

Граница: ошибка подключения до выполнения `executeMonitoredQuery` не обязательно создаёт этот цикл. Наличие любой записи ошибки также не означает бесконечный цикл — нужен повторно падающий запрос каталога и открытая панель.

Рекомендация: событие журнала должно обновлять только состояние журнала; загрузку каталога отделить от полного снимка и запускать по открытию HTTP-панели, явному обновлению и смене БД. Добавить объединение параллельных обновлений и контролируемый повтор после ошибки.

Проверка: изолированно исполнен текущий `SettingsViewProvider`, с подставленным сервисом, моделирующим событие журнала при ошибке каталога. Один `postState` вызвал четыре загрузки подряд; mock намеренно остановил генерацию событий на четвёртой загрузке. Это подтверждает повторный вход, но не является проверкой PostgreSQL или Extension Host.

## 2. P1: запуск MCP не доказывает выбранную БД

Источники: `clientMcpService.ts:68-100`; для сравнения корректная проверка имени БД есть в `waitForServer:141`.

`changeRunning('start')` возвращает `{ changed: false }`, если `/health` отвечает `ok`, не сравнивая БД сервера с выбранной. После собственного запуска проверка готовности также сравнивает только `status`. Поэтому уже работающий сервер другой БД воспринимается как достаточный; при гонке запуска ответ чужого сервера может подтвердить успех. Статус UI отдельно показывает несовпадение, но операция запуска его не устраняет.

Рекомендация: определить явную политику несовпадения (сообщить ошибку либо выполнить согласованное переключение); проверять имя ожидаемой БД перед no-op и после запуска. Не подписывать каталог ожидаемой БД до такой проверки. Имя БД само по себе также не доказывает идентичность хоста.

Проверка: текущий `ClientMcpService` исполнен с `/health = { status: 'ok', database: 'other_database' }` и выбранной `selected_database`. Получен `{ changed: false }`. Реальный процесс не запускался.

## 3. P2: потеря изменений и конкурирующие переходы MCP

Источники: `clientMcpService.ts:45-65,115-139`; `settingsViewProvider.ts:40-44,266-281`.

`scheduleDatabaseSync` отбрасывает новые события, пока есть `databaseSync`. Повторного прохода после завершения нет. `refreshTools` заново читает выбор и может исправить раннее переключение, но изменение, пришедшее после чтения options в этом последнем проходе, уже теряется. Например: каталог обновляется для B; пользователь выбирает C; событие игнорируется; операция заканчивается на B.

Кроме того, ручные `changeRunning` и `refreshTools` не включены в общую очередь с синхронизацией. Обёртка `setClientMcpServerRunning` ловит ошибки и не возвращает их сервису: после неудачной остановки `syncDatabase` может продолжить запуск и обновление каталога. Автоматическая синхронизация вызывает `refreshTools(true)` даже для offline MCP; эта функция способна временно запустить сервер для получения каталога. Это поведение следует явно определить как продуктовую политику.

Рекомендация: одна очередь переходов с последним запрошенным выбором, повторным проходом при изменении и проверкой конечной БД. UI должен отображать результат операции, а сервис — владеть последовательностью и получать ошибки напрямую.

Статический сценарий; живое быстрое переключение профилей не проверялось.

## 4. P2: гонки снимков и необработанные ошибки Promise

Источники: `settingsViewProvider.ts:37,65,69,93,326-417`.

Таймер, журнал, конфигурация, открытие панелей и сообщения запускают независимые `postState`. Нет общей выполняющейся операции, номера снимка или проверки актуальности. Старое медленное обновление может завершиться после нового и перезаписать состояние UI. Внутри одного снимка роль и конфигурация читаются раньше, а каталог методов и статус MCP — позже, поэтому смена БД во время ожидания может смешать данные разных выборов.

Большинство вызовов используют `void` без `catch`, в том числе оба обработчика сообщений. Ряд веток `handleMessage` не ловит ошибки: запись конфигурации/credentials, поиск значений параметров, навигация. Ошибка поиска оставляет `lookupLoading` в HTTP UI без ответного сообщения. Общий обработчик unhandled rejection в журнале не заменяет завершение конкретного действия UI и тоже инициирует обновление состояния.

Кэш knowledge MCP хранит только время и значение, без ключа workspace/env. Внешняя смена env или workspace может до 30 секунд показывать прошлый результат; параллельные проверки также не объединяются.

Рекомендация: объединять обновления, отбрасывать устаревшие результаты по поколению выбора, ключевать кэш источником и ловить ошибки на границе сообщений с корректным ответом UI.

## 5. P2: HTTP-панель не получает периодический статус самостоятельно

Источники: `settingsViewProvider.ts:69-75,79-99`.

Таймер создаётся только в `show()` и обновляет состояние только при видимой панели **настроек**. При открытой отдельно HTTP-панели таймера нет; при скрытых настройках он не выполняет обновление. Если тестовый HTTP-процесс завершится извне, отображение может остаться прежним до следующего сообщения, события журнала или изменения видимости. `HttpApiService.getServerState` проверяет процесс только при обращении, отдельного события завершения для UI здесь нет.

Рекомендация: подписать HTTP UI на завершение процесса либо обновлять его статус при видимости HTTP-панели независимо от настроек. Не использовать для этого полную загрузку всех каталогов.

## 6. P3: границы UI и сервисов ещё широкие

`SettingsViewProvider` одновременно владеет двумя панелями, маршрутизацией сообщений, агрегированием состояния, knowledge MCP-кэшем, записью rdboadm.ini и публичными HTTP-операциями. `SettingsServices` использует `Pick` от конкретных классов и объединяет операции с изменяемыми полями каталога. Адаптер агента зависит от полного типа провайдера, хотя ему нужны только HTTP-операции. `startHttpTestServer` и `stopHttpTestServer` ждут `postState` после выполненной операции — открытая UI-панель может задержать ответ агента проверкой knowledge MCP, чтением файлов и запросами БД.

Дополнительная неоднозначность: при отсутствующем настроенном профиле UI подставляет первый профиль (`settingsViewProvider.ts:356-357`) без изменения настройки. Это маскирует недействительный выбор; точный фактический fallback нужно проверять отдельно в resolver профиля.

## Минимальные обязанности и контракты перед возможным рефакторингом

| Модуль | Единственная ответственность | Минимальный контракт |
| --- | --- | --- |
| registerSettings | Сборка области и регистрация команд/освобождения | Входные зависимости, публичные действия области |
| SettingsViewProvider | Жизненный цикл панели настроек и доставка её сообщений | show, refresh, dispose |
| HttpApiViewProvider | Жизненный цикл HTTP-панели и её сообщений | show, dispose; узкие HTTP-действия в зависимостях |
| SettingsStateController | Актуальный снимок настроек и объединение обновлений | read/refresh, событие состояния, dispose |
| ClientMcpService | Последовательные переходы и каталог для конкретного выбора | start/stop/sync/refreshTools, снимок статуса |
| HttpApiService | HTTP-вызовы, каталог и жизненный цикл тестового процесса | Операции HTTP, снимок/событие сервера, dispose |

Это предложение, не выполненный рефакторинг. Начать следует с пунктов 1–4 без масштабного перемещения файлов. Выделять HTTP-панель стоит только после стабилизации поведения. Не добавлять отдельные модули, которые лишь пересылают вызовы.
