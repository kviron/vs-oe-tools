# База знаний vc-ve-tools

> Актуальный срез: 15 сентября 2026 года, версия `0.5.0`.
>
> Документ фиксирует текущее устройство расширения, реализованные сценарии,
> важные технические решения и границы проверенного поведения. Историю отдельных
> релизов см. в [`CHANGELOG.md`](../CHANGELOG.md).

## 1. Назначение проекта

`vc-ve-tools` — расширение VS Code для разработки и сопровождения проектов
«Восточного Экспресса». Оно объединяет работу с исходниками проекта,
метаданными PostgreSQL, нативным клиентом, производственными задачами, пакетами,
SVN, SQL-инструментами и MCP в одном интерфейсе.

Основной принцип проекта: не подменять штатные механизмы Восточного Экспресса
там, где важны аудит, пакетная принадлежность и нативная семантика. Чтение может
идти напрямую из базы, но изменения метаданных должны проходить через
контролируемый репозиторий расширения либо через методы нативного клиентского MCP
с обязательной проверкой результата.

## 2. Архитектура

Расширение организовано как модульный монолит с отдельным Vue-приложением для
webview-интерфейсов.

| Слой | Назначение | Основные пути |
| --- | --- | --- |
| Точка входа | Минимальная активация расширения | `src/extension.ts` |
| Композиция | Регистрация команд, панелей, сервисов и жизненного цикла | `src/application/` |
| Общие контракты | Идентификаторы, типизированные сообщения webview | `src/core/` |
| Функции продукта | Изолированные предметные области | `src/features/` |
| Интеграции | PostgreSQL, конфигурация проекта, логирование | `src/infrastructure/` |
| MCP расширения | Локальный сервер и каталог инструментов | `src/mcp/` |
| Webview UI | Vue 3, Vite, shadcn-vue, Hugeicons, CodeMirror | `webview-ui/` |
| Нативные адаптеры | Исходники и инструкции для методов OE | `native/` |
| Проверки | Mocha/VS Code integration tests | `src/test/` |

Крупная функция добавляется отдельной папкой в `src/features`. SQL хранится в
репозиториях, VS Code-панели — в менеджерах представлений, обмен с Vue — через
`src/core/webviewProtocol.ts`. Общие элементы интерфейса берутся из
`webview-ui/src/components/ui` и выдерживаются в едином компактном стиле
shadcn-vue/Hugeicons.

## 3. Источники данных и границы доверия

Расширение работает сразу с несколькими контурами:

1. **Проект на диске.** `Vars.bat`, `bin\\rdboadm.ini`, PKF, Pascal, DFM и SVN
   рабочей копии. Текстовые файлы Восточного Экспресса обрабатываются с учетом
   Windows-1251.
2. **Выбранная проектная PostgreSQL-база.** Используется для поиска и просмотра
   метаданных, SQL-инструментов, истории и части контролируемых операций.
3. **Нативный клиентский MCP.** Запускается через `OEExecTask.exe` в выбранном
   профиле и предоставляет штатные операции над метаданными.
4. **Производственная база через OENP.** Используется рабочим пространством
   задач; доступ к ней должен оставаться read-only, пока отдельная операция
   изменения не согласована и не проверена.
5. **Локальный MCP расширения.** Дает ИИ-агентам безопасный каталог поиска,
   чтения, навигации, диагностики и ограниченных действий.

Выбранный профиль и реально активная база — разные доказательства. Перед
операцией, зависящей от окружения, нужно подтвердить и профиль расширения, и
`current_database()`/`get_active_database`. Наличие URL или файла конфигурации не
доказывает, что нативный HTTP/MCP-сервис действительно слушает порт.

## 4. Реализованные рабочие пространства

### 4.1. Проводник и карточки метаданных

- поиск и навигация по пакетам, классам и объектам;
- карточка класса со счетчиками методов, атрибутов, свойств и объектов;
- фильтрация членов класса и визуальное различение групп классов;
- открытие объекта по ID из буфера обмена и копирование ID;
- отдельные карточки методов, атрибутов, свойств и объектов;
- переход от сущности к владельцу, пакету и исходному объекту.

Карточка метода показывает метаданные, подсвеченную сигнатуру, владельца и
пакет. Код не дублируется в свойствах: он открывается в отдельном виртуальном
редакторе VS Code.

Карточка атрибута поддерживает просмотр, создание и редактирование. Действия
доступны из самой карточки и контекстного меню. Сохранение выполняется через
нативный клиентский MCP с валидацией схемы, проверкой конкурентного изменения,
повторным чтением результата и предупреждением о проблемах пакетной привязки.

### 4.2. Редакторы методов, SPU и DFM

- методы открываются через схему `vc-ve-method` и сохраняются с учетом
  Windows-1251;
- изменение метода регистрируется в `LogCChangedObject` внутри общей транзакции;
- доступны история файла/метода, история выделенного фрагмента, SVN diff,
  history и blame;
- SPU редактируются в отдельном представлении с общим CodeMirror-редактором;
- DFM можно просматривать и редактировать, включая разрешение наследования.

Создание методов из UI сохраняется. Публичный MCP-инструмент расширения
`create_class_method` удален в `0.5.0`; штатный инструмент нативного клиента
`class_method_add` не удалялся.

### 4.3. Синхронизация пакетов

- просмотр отличий между метаданными базы и PKF;
- реконструкция meta-PKF, включая файлы, содержащие только члены класса;
- определение класса-владельца через `SeniorID`;
- просмотр изменений и конфликтов SVN;
- отдельный workflow разрешения merge-конфликтов;
- read-only диагностика нарушений пакетных границ с показом владельца ссылки,
  целевого объекта, обоих пакетов и рекомендуемого файла.

PKF нельзя исправлять прямой записью в обход модели. Для изменения метаданных
используется цепочка `class_member_get` → полное изменение через
`class_method_change`/`class_attribute_*` → повторное чтение. После этого штатная
синхронизация обновляет PKF.

`bind_objects_to_package` предназначен только для новых объектов с
`Abstract.SysFile IS NULL`. Он намеренно не переносит уже привязанный метод
между пакетными файлами. Такой метод переносится через интерфейс пакетов или
редактор метаданных в нужный файл, например `Консультант → Класс_Объект`,
после чего привязку нужно перечитать и проверить.

Для сериализации meta-PKF должен быть найден ровно один владелец среди связей
класса, члена и значений `SeniorID`. Неоднозначное владение считается ошибкой,
а не поводом выбрать первый найденный объект.

### 4.4. SQL-инструменты и диагностика

- SQL-исполнитель с подсказками схемы и историей запросов;
- SQL-монитор через совместимый `OESQLMonCon.exe`;
- резервный поиск коллектора в соседней установке R306;
- отдельные панели нативных логов, логов расширения и недавних ошибок;
- большие логи открываются в переиспользуемом read-only редакторе.

MCP-инструмент произвольного SQL допускает только read-only запросы. Проверка
синтаксиса и категории запроса выполняется до обращения к базе.

### 4.5. HTTP API Workbench

Рабочее пространство HTTP API отделено от настроек и поддерживает три сценария:

| Режим | Для чего используется |
| --- | --- |
| Прямой вызов | Запуск выбранного обработчика отдельным `OEExecTask.exe` без HTTP-сервера |
| Тестовый сервер | Реальный HTTP-запрос к временному серверу OE с одним разрешенным методом |
| Ручной запрос | Произвольный URL, метод, заголовки и тело |

Общие возможности: каталог и поиск методов, подсветка сигнатуры, форма
параметров из метаданных, подсказки ссылочных значений, строгие даты/время,
JSON-параметры, cURL/Postman-представление, история запросов и CodeMirror-просмотр
ответа. При открытии списка он прокручивается к выбранному методу.

При смене метода тестового сервера запуск сериализован: старый сервер
останавливается, затем запускается новый с точным allowlist. Wildcard `*` больше
не используется, поэтому не возникает гонки между старым и новым набором
разрешенных методов.

Прямой режим использует нативный метод
`RDBOHTTPServer.Разработка_HTTPТестСервер` (`3200176`) и файловый протокол
`vcve-direct-v1`. Для шаблонных обработчиков выбранный HTTP-объект передается
явно, что устраняет ошибку загрузки кэш-объекта с `ID = 0` у семейства методов,
использующего `HttpМетодПоШаблону`.

Границы прямого режима:

- это не HTTP-запрос, поэтому заголовки, HTTP-аутентификация, сессия и загрузка
  файлов не эмулируются;
- `HttpDataStream` заранее отклоняется;
- автоматических повторов и fallback-вызовов нет, поскольку обработчик может
  менять данные;
- отмена или timeout не откатывают уже выполненные изменения;
- нативный метод `3200176` расширение автоматически в базу не устанавливает.

Подробный нативный контракт описан в
[`native/http-api/README.md`](../native/http-api/README.md).

### 4.6. Производственные задачи

- отдельное рабочее пространство и карточка задачи;
- фильтры по ответственному, статусу, проекту, приоритету, типу работы, релизу
  и просрочке;
- настройка колонок, сводные показатели и компактные семантические бейджи;
- поиск по номеру и содержимому, загрузка полной карточки и истории;
- переходы по ссылкам на задачи и объекты из описания;
- вложения с поддержкой нативного `Smallint`, в том числе поля
  `StoredFiles.Important`;
- безопасный plain-text fallback для описания;
- отложенная загрузка `Comment_Rich`, разбор RTF и восстановление встроенных PNG,
  JPEG и WMF-изображений с сохранением позиции в тексте.

Регрессионный сценарий задачи №88212 проверил длинное RTF-описание со встроенной
WMF-картинкой между двумя текстовыми блоками. WMF преобразуется в PNG локально,
не меняя исходное описание задачи.

## 5. MCP и автоматизация

### MCP расширения

Локальный сервер сгруппирован по предметным инструментам, а регистрация хранится
в `src/mcp/tools/index.ts`. Основные группы:

- активная база, список профилей и переключение базы;
- поиск классов, методов и объектов, разрешение ссылки на метод;
- чтение классов, методов, атрибутов, свойств, словаря и DFM;
- навигация в Explorer, карточки и виртуальный редактор;
- read-only SQL, история SQL, логи и диагностика;
- Package Sync, SVN history и производственные задачи;
- управление клиентским MCP, нативным клиентом и HTTP-тестовым сервером;
- обновление базы, пакетов и бинарных файлов;
- контролируемое сохранение исходника существующего метода.

Сгенерированные файлы не являются источником истины. После изменения каталога
MCP нужно запускать `npm.cmd run check:generated`.

### Клиентский MCP

Жизненный цикл сделан явным:

1. `start_client_mcp` запускает или синхронизирует нативный процесс с выбранной
   базой.
2. `list_client_mcp_tools` получает живой каталог и сохраняет его для
   отображения.
3. `call_client_mcp_tool` вызывает только обнаруженный инструмент.
4. `stop_client_mcp` завершает управляемый процесс.

Повторный запуск требуется, если активная база изменилась. Доступность URL не
заменяет проверку каталога и безопасный read-only smoke test, например
`validate_sql` с `SELECT 1`.

## 6. Правила изменения метаданных

Перед любой мутацией необходимо:

1. Подтвердить целевой проект, профиль и фактическую активную базу.
2. Прочитать текущий объект и зафиксировать его ID, владельца и пакет.
3. Передавать полный исходник метода, а не частичный patch.
4. Использовать нативный клиентский MCP для создания или изменения метаданных,
   если операция должна повторять поведение штатного клиента.
5. Повторно прочитать объект и проверить сигнатуру, код и пакетную привязку.
6. Дать Package Sync сформировать изменение PKF.

Нельзя напрямую редактировать PKF, удалять зависимости SQL-командами или
продолжать цепочку создания, если `check_object_package_binding` показывает
отсутствующую/неверную привязку.

## 7. UI-соглашения

- интерфейс компактный и согласован с VS Code;
- компоненты берутся из shadcn-vue, иконки — из Hugeicons;
- повторяющиеся состояния оформляются через общие `Card`, `Tabs`, `Table`,
  `Field`, `Alert`, `Dialog`, `Command`, `Badge`, `Spinner` и `Empty`;
- длинные данные открываются в редакторе или модальном окне, а не расширяют
  строку таблицы;
- идентификатор должен копироваться и открываться без ручного поиска;
- сборка Vue подтверждает типы и шаблоны, но не считается визуальной проверкой
  Development Host.

## 8. Проверка изменений

Базовый набор команд:

```powershell
npm.cmd run check:release
npm.cmd run check:generated
npm.cmd run check-types
npm.cmd run lint
npm.cmd test
npm.cmd run package
```

Выбор проверок зависит от риска, но для релиза обязательны `check:release`, полный
набор тестов и production-сборка. Нативные интеграции дополнительно проверяются
на целевой базе с readback. Unit/integration tests не заменяют проверку
установленного VSIX, Extension Development Host, доступности OENP или поведения
реального клиента.

Перед заявлением о готовности нужно разделять четыре уровня доказательств:

| Уровень | Что доказывает |
| --- | --- |
| Типы, lint, сборка | Исходники согласованы и собираются |
| Автотесты | Зафиксированные контракты не регрессировали |
| Нативный smoke/readback | Интеграция работает в конкретной базе и профиле |
| Development Host/VSIX | Реальный интерфейс и упаковка работают для пользователя |

## 9. Релизный процесс

Правила задает [`CONTRIBUTING.md`](../CONTRIBUTING.md):

1. Выбрать SemVer по пользовательскому влиянию. До `1.0.0` несовместимое
   изменение повышает `MINOR`.
2. Синхронно изменить версии в `package.json`, `package-lock.json` и корневой
   записи lock-файла.
3. Добавить датированный раздел в `CHANGELOG.md`.
4. Выполнить релизные проверки, тесты и production-сборку.
5. Проверить содержимое VSIX, а не только `.vscodeignore`.
6. Создать Conventional Commit `chore(release): prepare X.Y.Z` и тег `vX.Y.Z`.
7. Хранить локальный VSIX только в игнорируемом `releases/`; публикация и push —
   отдельные действия.

На момент этого среза локально подготовлен и помечен тегом `v0.5.0`. Ветка
`origin/main` оставалась на `v0.4.0`; публикация `0.5.0` не подтверждена.

## 11. Известные ограничения и риски

- Поведение зависит от версии конкретного проекта, структуры метаданных и
  совместимости нативных бинарных файлов.
- Наличие настроенного клиентского MCP не гарантирует, что живой процесс и его
  каталог доступны.
- После аварии `OEExecTask.exe` нужно анализировать свежий `.stack`; повторный
  запуск без диагностики может повторить побочный эффект мутирующего метода.
- Сложные или неоднозначные meta-PKF нельзя реконструировать выбором случайного
  владельца; требуется явное разрешение модели.
- Производственные задачи по умолчанию являются read-only контуром.
- Прямой HTTP-вызов не заменяет проверку настоящего endpoint для обработчиков,
  зависящих от HTTP-контекста.
- Секреты, временные профили, логи, сетевые captures, диагностические базы,
  сгенерированные CSV, `releases/` и `*.vsix` не коммитятся.

## 12. Как поддерживать эту базу знаний

Обновляйте документ при изменении архитектурной границы, пользовательского
workflow, нативного контракта, правил безопасности или релизного процесса.
Детальный список пользовательских изменений остается в `CHANGELOG.md`, а здесь
должны сохраняться только актуальные правила и устойчивые решения.

При обновлении:

- меняйте дату и версию среза;
- удаляйте устаревшее поведение, а не накапливайте взаимоисключающие инструкции;
- для временного статуса явно указывайте дату;
- добавляйте ссылку на подробный runbook вместо копирования большого протокола;
- проверяйте существование всех относительных ссылок.
